## 1회차 — 새 에디터 만들기

### 요청

1. 설비를 라이브러리에서 골라 직접 배치
2. 사용자 모델을 라이브러리에 추가
3. 라이브러리를 **설비 / 연결장치** 탭으로 구분
4. 연결장치는 거리에 따라 **모델이 연장**되고 **커브**도 되어야 함, 설비 근처에서 **스냅**
5. 팩토리오 · 새티스팩토리 같은 느낌
6. 설치 뷰는 **탑뷰**로 전환
7. 작은 그리드 단위로 스냅 (스타크래프트 건물 짓듯)
8. **질문 —** 컨베이어가 물리려면 유입·유출부가 필요할 텐데, 모델을 어떻게 만드는 게 좋을지

### 답변 (8번 질문)

**3ds Max에서 50mm 짜리 작은 박스를 만들어 `PORT_IN@X-` / `PORT_OUT@X+` 로 이름 붙여
같이 내보내세요.**

| 왜 | |
|---|---|
| **더미 헬퍼가 아니라 박스** | 자식 없는 헬퍼는 익스포터·버전에 따라 노드가 통째로 빠집니다. 메시는 안 빠집니다 |
| **`@X+` 접미사** | 방향 판정은 ①이름 접미사 ②노드 회전 ③bbox 기준 순인데, CAD 익스포트는 Z-up→Y-up 변환 때문에 회전이 의도대로 안 실립니다. 접미사는 그 사고가 없습니다 |
| **마커의 높이(Y)가 핵심** | 그 값이 그대로 벨트면 높이가 됩니다. **바운딩 박스로는 절대 알 수 없는 유일한 값**이라, 포트 없는 모델은 "높이 45%" 로 찍을 수밖에 없습니다 |
| **연결장치는 IN/OUT 사이 거리 = 1피치** | 프레임이 앞뒤로 튀어나와도 피치가 정확히 지켜지고 여유살은 옆 토막과 겹쳐 맞물립니다. bbox로 재면 마디마다 틈이 벌어집니다 |

이름이 `PORT_` 로 시작하는 노드는 자동으로 숨기고 바운딩 박스 계산에서도 뺍니다.
포트가 없는 모델도 동작하도록 bbox 4방향에 임시 포트를 자동 생성하고,
그 사실을 UI에 표시합니다.

### 만든 것

Vite + React + react-three-fiber. 탑뷰(정사영)에서 배치하고 3D(원근)에서 확인하는 두 뷰.

- **연장 방식** — 경로 길이 ÷ 토막 길이를 반올림해 타일 개수를 정하고, 남는 오차만
  미세하게 늘려 **틈 0** 으로 맞춤
- **커브** — 아래 "커브 처리" 항목 참고
- **스냅** — 5cm~1m 그리드 + 인접 설비 **면 맞춤**(0.6m 안에 들어오면 면끼리 딱 맞춤)
- **회전** — 라디안이 아니라 **0~3 정수(×90°)** 로 저장해 오차 누적을 없앰

### 커브 처리 — 두 번 갈아엎은 부분

| 시도 | 결과 |
|---|---|
| 타일을 그냥 늘어놓기 | 코너에서 각지고 틈이 벌어짐 |
| 코너에서 **타일을 잘게 쪼개기** | 21m L자 경로가 31타일. 롤러가 코너에서만 촘촘해져 **딴 물건**이 됨 |
| 구간별로 국소 분할 | 오히려 39타일로 악화 — 5.3m 기준 타일을 통째로 13등분하니까 |
| **원본 메시를 길이축으로 썰어 정점을 늘리기** ✅ | 타일 개수는 그대로(33개 × 1.01배), 각 타일이 경로를 따라 휨 |

정답은 "타일을 쪼개는 것" 이 아니라 **"원본 메시에 정점을 미리 늘려 두는 것"** 이었습니다.
디폼은 있는 정점만 옮기므로, 5m 상자는 양 끝에만 정점이 있어 코너를 직선으로 가로지릅니다.
삼각형 예산(40,000)을 넘지 않는 선에서 분할 수를 자동으로 낮춥니다.

## 2회차 — 레일 규칙 추가 + 모델 교체

### 요청

1. 레일 경로가 겹치면 더 높은 층으로 쌓기
2. 레일도 선택해서 층을 직접 지정
3. 새 레일은 다리 없는 형태 (가시화 목적)
4. 컨베이어 벨트에 UV 애니메이션
5. UV는 **두 개 채널로 서로 반대 방향**
6. 벨트 폭 1m, 사용자가 폭 수정 가능
7. 설비·벨트 GLB 교체, 테스트 모델 제거

### 모델을 열어 보고 알게 된 것

**① 포트 이름과 실제 위치가 어긋나 있었습니다.**
`PORT_IN@X-` 라고 적혀 있는데 마커는 `Z=+1.524`, 즉 **+Z 면**에 있었습니다.
이름대로 -X를 따르면 벨트가 설비 옆구리를 스치고 지나갑니다.

→ **마커 위치를 믿고 보정**하도록 했습니다(다른 축으로 3배 이상 & 0.25m 이상 치우쳤을 때).
위치는 형상에서 직접 읽은 값이고 이름은 손으로 적은 값이라, 어긋났을 때 틀렸을 가능성이
높은 쪽은 이름이기 때문입니다. 대신 조용히 넘어가지 않고 인스펙터에 노란 경고를 띄웠습니다.

**② 컨베이어는 bbox로 길이축을 가릴 수 없었습니다.**
1피치 **1.000m** 인데 폭이 **1.012m** — 오히려 폭이 더 깁니다. "긴 쪽이 길이축" 규칙이
정반대 답을 냅니다.

→ **벨트 윗면의 UV 기울기**로 판정하도록 했습니다. 텍스처가 흐르도록 펴 놓은 축이
곧 흐름 방향입니다. 판정 순서는 ①사용자 지정 ②IN/OUT 포트 ③벨트 UV ④bbox.

**③ 반송면 높이도 bbox로는 틀립니다.**
프레임 꼭대기 0.322m vs 벨트 윗면 0.142m — **18cm** 차이. 이름에 `Belt` 가 들어간
서브메시를 찾아 그 윗면을 반송면으로 씁니다.

### 5번 요청에 대한 답변 — "두 채널" 은 이미 필요 없었습니다

보내주신 벨트의 UV는 **이미 루프를 한 바퀴 감아 편 형태**였습니다.

```
윗면 :  U 0.789 → 2.034   (진행 방향으로 증가)
아랫면:  U 0.665 → -0.580  (진행 방향으로 감소)
```

**U 오프셋 하나만 흘려도 윗면과 아랫면이 저절로 반대로 움직입니다.** 실제 벨트가 도는
모습 그대로이고, 채널을 두 개 쓸 필요가 없습니다. 현재 GLB에는 `TEXCOORD_0` 하나뿐이라
두 번째 채널을 쓸 수도 없는 상태였습니다.

속도는 벨트 윗면 UV 기울기(측정값 **-1.245 U/m**)를 직접 재서 **m/s** 로 환산합니다.
모델의 UV 스케일이 바뀌어도 "0.6 m/s" 지정이 그대로 유효합니다.

> 만약 의도하신 게 "표면 무늬 + 정지된 음영" 처럼 **독립적인 두 레이어**를 겹치는 것이라면
> 그건 UV 채널이 아니라 텍스처 슬롯이 두 개 필요한 이야기입니다. 아직 미구현.

### 만든 것

- **자동 층 쌓기** — 교차만이 아니라 나란히 겹쳐 달리는 경우도 잡습니다(경로를 따라 찍어
  최단거리 판정). 같은 포트에서 갈라지는 두 벨트가 출발부에서 가깝다고 올라가지 않도록
  양 끝 1.5m는 제외. 층 간격 1.0m, 양 끝은 포트 높이를 지키고 가운데만 3m 경사로 들림
- **수동 층 조정** — 어느 레일이 위로 갈지는 결국 사람이 정하는 것이라, 자동 배정은 시작값
- **폭 조절** — 중심선 기준으로 좌우만 벌어지고 길이·높이는 유지

## 3회차 — 포트 이름 수정 확인 + 라이트 테마 + 연결 규칙

### 요청

1. `PORT_IN@Z+` / `PORT_OUT@Z-` 로 수정했으니 확인
2. 배경을 라이트 버전으로 (너무 어둡다)
3. *(중간 추가)* 입구↔입구, 출구↔출구는 연결 안 되게

### 답변

**① 확인 완료** — 이름과 마커 위치가 일치해서 보정 경고가 사라졌고, ①번 규칙(이름 접미사)
에서 바로 확정됩니다. 추측이 개입할 여지가 없어졌습니다.

덤으로 `IN`/`OUT` 판정 정규식도 고쳤습니다. `PORT_IN@Z+` 처럼 `@` 가 바로 붙으면
종류를 못 읽어 `any` 로 떨어지고 있었습니다. 이게 3번 요청과 직접 연결됩니다.

**② 라이트 테마** — UI 색을 전부 CSS 변수로 빼서 `bg-panel`, `text-ink` 같은
**의미 이름 하나만** 쓰도록 바꿨습니다. 새 UI를 추가할 때 라이트 대응을 빠뜨릴 수 없는
구조입니다. 3D 배경·바닥·그리드와 **조명 광량까지** 함께 바뀝니다 — 다크용 조명값을
그대로 쓰면 밝은 배경에서 모델이 배경보다 어두워져 실루엣만 남습니다.

**③ 연결 차단 — 세 겹으로**

| 단계 | 처리 |
|---|---|
| 스냅 | 이을 수 없는 포트는 회색으로 죽고 **달라붙지 않음** |
| 클릭 | 그래도 눌렀다면 이유를 띄우고 아무 일도 안 함 |
| 저장 | 유입부에서 시작해 유출부로 그려도 자동으로 뒤집어 **항상 "유출 → 유입"** |

여기서 실제 버그를 하나 잡았습니다. 스냅에서 빠진 포트를 클릭하면 **"빈 바닥" 으로 해석돼
엉뚱한 자유 끝점이 생기고 있었습니다.**

## 4회차 — 카트 + 연결장치 수정

### 요청

**카트**
1. 설비·연결장치 옆에 **카트 탭**
2. 경로를 먼저 그리면 그 경로를 **순찰**, 속도 조절
3. 카트 안의 `obj` 객체가 설비 **out**쪽에서 생기고 **in**쪽에서 사라짐
4. 설비마다 정하는 **갯수**만큼 층층이 적재

**연결장치**
1. 그린 다음 **직접 라인 수정**
2. 배관·전선은 **따로 위치 지정** (컨베이어 위치에서 생성되면 안 됨)
3. 배관은 **T·+ 모양**으로 겹치는 경우도

### 판단이 갈렸던 지점 — 정차역을 어떻게 정할 것인가

처음엔 "포트에서 3.5m 이내" 만 봤습니다. 그런데 Machine_1은 유입·유출부가 **앞뒤 면**에
붙어 있어서, 카트가 **옆구리를 스쳐 지나가도** 두 포트가 동시에 걸립니다.
→ **싣자마자 내리는** 우스운 동작이 됐습니다.

→ "포트가 열린 방향 쪽(±69° 이내)으로 지나갈 때만" 이라는 조건을 넣었습니다.
덕분에 옆을 지나는 경로는 역으로 치지 않습니다.

정차역을 따로 찍게 하지 않은 이유는, **"카트 경로를 설비 옆으로 지나가게 그린다"** 는
행동 하나로 적재·하역이 정의되면 따로 배선할 게 없기 때문입니다.

### 배관·전선을 자재 포트에서 떼어낸 이유

컨베이어와 같은 포트를 쓰면 배관이 벨트 높이(0.987m)에 걸립니다. 자재가 흐르는 물건이
아니라 설비 부속이므로 **자기 높이**(전선 4.0m 상부 · 배관 0.35m 바닥)에 놓입니다.

| 클릭한 곳 | 결과 |
|---|---|
| 같은 종류의 기존 배관 위 | **분기점(T·+)** — 그 배관을 따라 움직임 |
| 설비 위(0.8m 이내) | 설비에 붙는 접점 — 설비를 옮기거나 돌리면 따라감 |
| 그 외 | 자유 끝점 |

**겹쳐도 층을 쌓지 않습니다** — T·+ 로 만나는 게 정상이기 때문입니다.
(층 쌓기는 컨베이어·레일 전용)

### 검증 방식을 바꾼 지점

브라우저 패널이 숨겨진 환경이라 프레임을 돌릴 수 없었습니다(GPU 큐가 막힘).
그래서 카트 주행 계산을 `useFrame` 밖으로 빼서 **`stepCart` 순수 함수**로 만들고
Node에서 직접 검증했습니다.

검증 우회가 아니라 **로직이 프레임 콜백에서 빠져나온 것**이라 코드도 더 나아졌습니다.

## 5회차 — 벨트 위 자재

### 요청

`obj.glb` 를 컨베이어 벨트 위로도 흐르게. 생성 간격과 층수를 내보내는 설비에서 설정.

### 판단 — 간격을 시간이 아니라 거리로

"생성 간격" 은 시간으로 읽을 수도 있지만 **거리(m)** 로 잡았습니다.
시간으로 두면 벨트 속도를 바꿀 때마다 줄 간격이 흐트러지는데, 거리로 두면
**화면에 보이는 그대로가 설정값**이 됩니다. 대신 현재 속도 기준 **개/분**을 같이 표시해
생산율로도 읽히게 했습니다.

### 판단 — 층수는 카트와 같은 값

이미 있던 "한 번에 내보내는 수량" 을 **적재 층수**로 정리해서, 벨트에 흐르는 묶음과
카트가 싣는 묶음이 같은 설비 설정을 따르도록 했습니다.
한 설비가 내보내는 단위는 하나여야 앞뒤가 맞다고 봤습니다.

### 구현 — 개체를 하나씩 관리하지 않음

```
자재 위치 = offset + k × 간격   (k = 0, 1, 2 …)
offset 은 0 ~ 간격 사이를 반복
```

간격이 항상 정확하고, 속도를 바꿔도 줄이 흐트러지지 않고, 경로 길이가 변하면 개수만
자연스럽게 달라집니다. 슬롯을 미리 만들어 두고 경로 밖으로 나간 것만 숨겨서
**생성·소멸 비용이 아예 없습니다.**

## 6회차 — 카트 대수 + 버그 신고

### 요청

1. 카트 경로에 **몇 대 배치할지** 지정
2. **버그 —** 내보내기·불러오기하면 카트 경로가 사라짐

### 버그 원인

**저장 대상을 만드는 곳이 세 군데로 흩어져 있었습니다.**
자동 저장에는 `carts` 를 넣었는데, 툴바의 **저장**과 **내보내기**는 각자 객체를 만들면서
빠뜨리고 있었습니다.

→ 새로고침으로는 살아남는데 **저장 버튼을 누르는 순간 오히려 지워지는** 상태였습니다.

`layoutSnapshot(state)` 하나로 모으고 세 곳이 전부 그걸 쓰게 했습니다.
저장할 항목이 늘어도 한 곳만 고치면 됩니다.

### 배치 대수

1~10대. 출발 지점을 경로 길이만큼 고르게 나눠 서로 붙어 다니지 않고, 각 대마다 적재
상태와 정차를 따로 갖습니다.

**한계 —** 왕복(열린) 경로에 여러 대를 올리면 되돌아오는 카트끼리 스쳐 지나갑니다.
외길에서 마주 오는 차를 피할 방법이 없어서 생기는 한계라, 그 조건일 때만 안내를 띄우고
**고리로 순환**을 권합니다. 회피 로직은 미구현.

## 7회차 — 선반(랙)

### 요청

선반 모델을 만들어 넣을 테니, 카트가 선반에 오면 들고 있던 양만큼 쌓아 두게.
쌓인 수량을 OBJ 로 표현하고, 배치할 때 길이를 조절할 수 있게. 선반은 카트 탭에 넣고
탭 이름은 **운송/적재** 로.

### 모델을 열어 보고 정한 것 — 피치를 기둥 사이로 잰다

`Shelf.glb` 는 선반판(`E1/E2/E3`)과 기둥(`Bar-`/`Bar+`)으로 되어 있었습니다.

한 칸을 이어 붙일 때 **바깥 바운딩 박스(2.675m)** 로 재면 기둥 두께만큼 벌어져
마디마다 틈이 생기고 기둥이 두 개로 겹칩니다. **기둥 사이 거리(2.588m)** 로 재면
옆 칸의 기둥이 정확히 같은 자리에 오므로, 두 번째 칸부터 시작 기둥을 지워
이음매마다 기둥 하나만 남겼습니다.

### 이어진 요청 (같은 회차)

길이 최대 10칸, 한 칸 길이·단 수(1~10)·단 간격·한 단 적재수까지 모두 조절.

→ 이렇게 되니 **모델을 통째로 복제하는 방식이 성립하지 않습니다**(모델에는 3단이
구워져 있음). 모델을 **판 한 장 + 기둥**으로 분해해서 필요한 만큼 다시 쌓는 구조로
바꿨습니다. 그 결과 형상의 유일한 출처가 `core/shelf.js` 가 되어, 렌더·풋프린트·
카트 정차역이 모두 같은 값을 봅니다.

### 재고를 도면에 저장하지 않은 이유

카트가 자재를 부릴 때마다 도면이 바뀌면 자동 저장이 계속 돌고 화면 전체가 다시
그려집니다. 재고는 "배치 결과" 가 아니라 "지금 돌아가는 상황" 이라 별도 저장소
(`simStore`)에 두었습니다. 대신 인스펙터에 가득 채우기/비우기를 넣었습니다.

---

### 이어진 수정 — 자리를 갈라 동작을 정한다

카트가 선반 옆을 지날 때마다 상황에 따라 싣거나 부려서, 같은 선반에서 넣었다 뺐다
하는 동작이 나왔습니다. 판정 조건을 정교하게 다듬는 대신 **자리를 갈랐습니다.**

> 선반 앞뒤 양면을 길이 방향으로 반 갈라 **입고(녹색) · 출고(주황)** 구역으로 나눔.
> 녹색을 지나면 내려놓고, 주황을 지나면 실어 간다.

"어디로 지나가느냐" 가 곧 "무엇을 할 것이냐" 가 되어, 도면만 보고도 흐름이 읽힙니다.
여기에 **한 번 주고받은 역은 다른 곳을 거치기 전까지 다시 반응하지 않는** 규칙을 더해
왕복 경로의 진동을 막았습니다.

이 규칙은 한 번 잘못 잡았습니다. 처음엔 "역을 지나면" 기록했는데, 그러면 빈 카트가
입고 구역을 그냥 지나쳤다는 이유로 바로 옆 출고 구역이 막혔습니다.
→ **실제로 자재가 오갔을 때만** 들른 것으로 치도록 고쳤습니다.
그 과정에서 수량 계산을 `stepCart`(순수 함수)에서 호출부로 옮겼습니다 —
"몇 개가 실제로 옮겨졌는가" 는 재고와 수용량을 봐야 알 수 있어서
움직임 계산과 섞일 자리가 아니었습니다.

## 8회차 — 건물이 생기고, 물류가 생겼다

### 요청

바닥과 벽을 그리고, 벨트 끝에 쌓아 두는 것(적치대)과 밖으로 내보내는 것(트럭)을.
그리고 처음 여는 사람이 뭘 해야 할지 모르니 안내를.

### 구역을 나누는 방법을 두 번 바꿨다

처음에는 **꼭짓점 목록**이었다. 사각형을 그리려면 네 번 찍어야 했고, ㄱ자 모양은
여섯 번이었다. 사용자가 물었다 — 「사각형 두 번이면 금방 그릴 수 있는데」.

맞는 말이었다. 그래서 **덧그리기**로 바꿨다. 사각형을 겹쳐 그리면 합쳐지고,
겹치는 것은 의도된 동작이다(그래서 ㄱ자가 사각형 두 번이면 된다). 펜툴은 남겨
두었지만 이제 특별한 모양을 그릴 때만 쓴다.

### 정차역 거리를 3.5m → 1m 로

넓게 잡으면 지나가기만 해도 역이 됐다. 특히 **설비 하나의 유입·유출부가 앞뒤
면에 붙어 있어서**, 옆구리를 스쳐 지나가면 둘 다 걸려 싣자마자 내리는 동작이
나왔다. 거리를 좁히고 **포트 정면**만 인정하도록 했다 — 거리보다 방향이 답이었다.

### 안내가 거짓말을 하면 안 하느니만 못하다

따라 하기를 붙이고 나서 네 번 고쳤다. 없는 기능을 안내하고, 아무것도 안 했는데
1/7 로 체크되고, 부르는 칸 이름이 틀렸다. **안내는 도면을 보고 스스로 체크되게**
만들어 놓았는데, 그 「보는 눈」(`guideFacts`)이 화면과 어긋나면 그대로 거짓말이
된다. 안내를 늘릴 때마다 그 눈부터 맞춰야 한다는 것을 여기서 배웠다.

## 9회차 — 그리는 도구에서 **돌려 보는 도구**로

### 왜 방향을 틀었나

상용 도구(FlexSim·AnyLogic·Plant Simulation)를 조사해 보니 파는 것은 형상이
아니라 **처리량·재공·가동률·병목** 네 숫자였다. 도면은 그 숫자를 얻기 위한
입력이지 결과가 아니었다.

### 순서가 중요했다

    ① 시뮬 시계 → ② 지표 → ③ 고장·불량(OEE) → ④ 배치 비교

1·2 는 읽기만 해서 충돌이 없고, 3 은 **지표 정의를 바꾸므로** 표시 자리가 잡힌
뒤에, 4 는 지표가 확정돼야 뜻이 있다. 거꾸로 갔으면 세 번 다시 짰을 것이다.

### 이미 계산해 놓고 버리던 값

`halted`(적치대가 차서 상류가 줄줄이 서는 것)를 매 프레임 계산해서 **빨갛게
칠하는 데만** 쓰고 버리고 있었다. 시간으로 적분하면 그대로 가동률이고, 가장 오래
막힌 설비가 병목이다. 새로 잰 것이 아니라 **버리던 것을 주운** 것이다.

### 서는 이유를 갈랐다 — 화면은 같아도 푸는 방법이 다르다

    막힘(blocked)  내보낼 데가 없다      배치로 푼다
    굶음(starved)  재료가 안 온다        상류로 푼다
    무인(unmanned) 사람이 모자란다       인력으로 푼다
    고장(down)     MTBF 로 선다          정비로 푼다

넷 다 「붉게 서고 벨트도 선다」로 똑같이 보인다. 그래서 **이유를 안 나누면
화면만 보고는 아무것도 못 한다.** OEE 의 A·P·Q 가 각각 어느 것에서 나오는지도
여기서 정해졌다.

### 「다시 재기」가 570만 개/시간을 냈다

시간만 0 으로 되돌리고 누적 개수는 그대로 뒀다. **분자와 분모의 시작점이 같아야
한다** — `shippedStart` 를 잡아 이번 실행에 늘어난 만큼만 센다. 이 한 줄짜리
규칙이 나중에 반복 실행에서도 그대로 쓰였다.

### 두 번 밟은 함정 — 빌드가 통과하는 오류

1. `useMemo(..., [placed])` 를 구조분해 **위에** 둬서 매 렌더 TDZ
2. `simStep` 을 **import 없이** 써서 컨베이어를 그리는 순간 화면이 통째로 멈춤

둘 다 `vite build` 를 통과한다. **빌드는 문법만 본다.** 이때부터 「씬을 건드렸으면
한 번 띄워 보고 넘긴다」가 규칙이 됐다.

### 검증을 저장소로 옮겼다 (`npm test`)

그전까지 검증은 세션마다 임시 폴더에 다시 쓰였고 세션이 끝나면 사라졌다.
「169건 통과했다」는 말만 남고 **다시 돌릴 방법이 없었다.** 저장소에 넣으니
다음 사람이 손대기 전에 「지금 멀쩡한가」를 물을 수 있게 됐다.

## 10회차 — 시간·원인·돈

### 설비마다 공정 시간

그전까지 설비의 속도는 **벨트 간격의 함수**였다. 간격을 좁히면 그 기계가 갑자기
빨라졌다. 만드는 것은 설비가 공정 시간대로 하고 벨트는 **출력 자리에 있는 것만**
가져가도록 갈랐다. 그러자 간격은 **정하는 값이 아니라 따라 나오는 값**이 됐다.

### 「막혔다」는 결과지 원인이 아니다

빨갛게 선 설비를 눌렀을 때 「막힘」이라고만 하면 아무 말도 안 한 것이다. 막힌
이유는 대개 **하류 어딘가**에 있다. 원인까지 거슬러 올라가 짚는 `diagnose.js` 가
여기서 나왔다.

### 원가 — 「남는 장사인가」

처리량은 답하는데 그 질문에는 못 답하고 있었다. 단가를 사람이 적게 하고(기본값
그대로면 그 공장의 원가가 아니라고 화면이 밝힌다), **가동 kW 와 서 있을 때 kW 를
나눠** 받았다. 한 값만 쓰면 서 있는 설비가 공짜가 되고, 그러면 **잔뜩 깔고 놀리는
배치가 원가에서 이긴다.**

### 아래 띠로 옮긴 이유

인스펙터에 지표·원가·병목을 다 넣었더니 3D 씬이 세로로 눌렸다. 씬은 16:9 로
남기고 숫자는 아래 띠로 내렸다. 띠도 한 화면에 다 안 들어가 **탭**으로 나눴다 —
나중에 「여러 판」이 셋째 탭으로 붙은 것도 같은 이유다(5 열은 안 들어간다).

## 11회차 — 꺼내 쓰기 · 나눠 쓰기

CSV 는 엑셀에서 다시 따질 때 쓰는 것이고, **사람이 읽는 것**은 따로 필요했다.
HTML 한 장으로 뽑아 브라우저에서 Ctrl+P 하면 PDF 가 된다.

공유는 Vercel Blob 에 올린다. **자물쇠가 없다** — 주소만 알면 누구나 올리고,
올라간 도면은 링크로 아무나 연다. 서로 돌려 보는 용도라 그대로 두기로 했고
(사용자 판단), 대신 올리는 창이 「누구나 열어 볼 수 있습니다」를 못 박아 말하고
확인을 한 번 더 받는다. **서비스로 낼 거면 여기부터 손대야 한다.**

## 12회차 — 돌리기 전에 답하기

### 라인 능력 (`balance.js`)

그때까지 「이 배치가 얼마나 만드나」를 알려면 **돌려 봐야** 했다. 그런데 설비마다
공정 시간이 있고 벨트마다 속도가 있으니, 도면만 보고도 천장은 계산된다.
돌리기 전에 나오는 값이 있으면 **배치를 그리는 동안** 고칠 수 있다.

### 따라 하기를 갈래로

한 줄짜리 40걸음은 아무도 안 끝낸다. 궁금한 것만 골라 밟도록 여덟 갈래로 나눴다.
그 과정에서 「골라 주세요」가 **늘 떠 있던 것**과 `crew` 두 걸음이 **서로 반대
선택을 요구하던 것**이 나왔다 — 갈래 하나에 문구를 하나만 두면 둘 중 하나는
반드시 틀린 말이 된다.

### 불량은 **만든 설비의** 문제다

불량률이 라인 전체의 OEE 품질 항을 깎고 있었다. 남이 만든 불량이 내 OEE 를
끌어내리면 어느 설비를 고쳐야 하는지 알 수 없다.

## 13회차 — 「그래서 얼마 이득인가」

### 두 모듈 사이에 답이 있었다

    balance.js   「제작기2 를 고치면 5 → 10개/분」
    cost.js      「지금 개당 1,240원」

실제로 하는 질문은 그 **사이**에 있다 — 「제작기를 한 대 더 놓을까?」 설비를
더 놓으면 **분모(개수)와 분자(돈)가 함께** 커지고, 어느 쪽이 더 크게 커지느냐가
답이다.

**「푼다」가 종류마다 다르다는 것이 요점이다.** 설비는 전력·고정비·사람이 따라
붙고, 벨트는 **돈이 안 든다.** 그래서 벨트가 병목이면 그것은 **공짜로 고칠 수
있는 병목**이다 — 이 한 줄이 설비를 사려다 말게 한다.

### 판정을 셋으로 나눴다

처음에는 이득/손해 둘이었다. 그런데 「전부 두 배로 늘리기」는 개당 원가가 **똑같이**
나온다(분모도 분자도 두 배). 그걸 「밑지는 장사」라고 찍고 있었다.
이겼다 / 그대로 / 밑진다 — 셋이라야 사실이다.

그리고 `won()` 이 3.03원과 2.87원을 **둘 다 「3원」으로** 찍었다. 견주라고 만든
자리에서 차이를 반올림해 없애고 있었다.

### 구역이 말을 하게 · 자(치수 재기)

구역에 이름만 있고 아무 값도 없었다. 찬 비율·인원·시간당 비용·지나는 카트를
붙였다. 자는 「이 벽에서 저 설비까지」를 재는 것이라 **바닥 밖도 잰다**(일부러 안
막았다). 자를 켰는데 「지울 대상을 클릭하세요」가 떠 있던 것은 사용자가 신고했다.

## 14회차 — 화면 없이 도는 라인

### 왜 뜯었나

상용 시뮬레이터와 견주어 가장 큰 구멍은 **「한 번 돌린 값 하나로 배치를 말한다」**
였다. 고장도 불량도 확률이라 한 판은 운이 섞인다. 그런데 여러 판을 돌리려면
화면 없이 돌아야 하는데, 시뮬이 **세 곳의 `useFrame` 안**에 있었다 —
SimClock 30줄 · BeltItems 19줄 · CartView **144줄**.

### 옮겨 적은 것이 아니라 **그릇을 바꾼 것**이다

「헤드리스 엔진을 새로 짜면 규칙이 두 벌이 되어 화면과 표가 어긋난다」는 걱정이
줄곧 있었다(그래서 배치 비교는 사람이 돌려 박제하는 방식이었다). 열어 보니
규칙은 이미 전부 순수 함수였고 컴포넌트에 남은 것은 **상태를 담는 그릇**뿐이었다.
useRef·useState 에 흩어진 일곱 조각이 `unit` 객체 하나가 됐고, 그래서 화면도
헤드리스도 **같은 함수**를 부른다.

### 물류 동선 · 리드타임

배치를 옮겨서 달라지는 값은 셋째였다 — **물건이 오가는 거리.**

    운반 작업량 = Σ (시간당 개수 × 그 구간 거리)      [m·개/시]

견주는 잣대는 **「한 개가 지나는 거리」**다. 총 작업량은 라인이 빨라지기만 해도
커져서, 배치를 나쁘게 고쳐 놓고도 숫자가 줄어 보인다.

화면에 띄우자마자 **단위가 어긋나 있었다** — 벨트는 300개/시인데 카트가 926개/시.
벨트는 「실제 흐르는 양」인데 카트는 **「나를 수 있는 최대」**였다. 성질이 다른
둘을 한 표에서 더했으니 총계가 아무 뜻이 없었다. 고치니 개당 거리가 116m → 53m.

### 검사가 **늘 통과하고 있었다**

`` new RegExp(`\b${one}\b`) `` — 템플릿 리터럴 안의 `\b` 는 단어 경계가 아니라
**백스페이스 문자(코드 8)** 다. 그 검사는 처음부터 아무것도 안 보고 있었다.
소스를 일부러 망가뜨렸더니 **0건 실패**가 나와서 알았다.

> **규칙**: 검사를 새로 쓰면 **일부러 깨뜨려 보고** 무는지 확인한다.

### 커밋 안 한 채 파괴 테스트 — 두 번 잃었다

검사가 무는지 보려고 소스를 망가뜨린 뒤 `git checkout -- src/` 로 되돌렸는데,
**새 파일은 untracked 라 복구가 안 된다.** 파괴 편집이 그대로 남았다(검사가 잡아
줘서 알았다).

> **규칙**: 파괴 테스트는 **커밋한 뒤에** 한다.

## 15회차 — 견주는 자리에 판정을 붙이고, 절반만 돌던 것을 찾았다

### 배치 비교에 판정

여러 판을 돌려 놓고 정작 견주는 자리에서는 한 판짜리 숫자를 나란히 놓고 있었다.
「412 대 405」를 눈으로 고르는 셈이라 **흔들림 안에 들어가는 차이를 차이라고
읽게 된다.** Welch t검정으로 「구간이 0 을 품는지」를 가른다.

**판 수와 길이는 사람이 못 고르게 두었다.** 견주는 자리에서는 판 수가 같아야
공정하다 — 한쪽만 20판 돌려 구간을 좁히면 판정이 그쪽 손을 든다.

### 「잡히기는 했는데 한 번도 안 서는 역」

인수인계에 「끝까지 못 봤다」로 남아 있던 도면(적치대 둘 → 조립기 하나)을 돌리려
했더니, 막고 있던 것은 **한 줄**이었다.

    globalThis.self = globalThis      ← three 의 워커 감지가 self 를 읽는다

three 의 GLTFLoader 가 Node 에서 그냥 돈다. 텍스처만 못 읽고 노드 이름·좌표·
바운딩 박스는 전부 나온다. **이제 실제 모델 치수로 도면을 세워 돌린다.**

돌려 보니 역은 넷 다 잡혔는데 **적치대 하나는 첫 바퀴 말고는 안 썼다.** 카트는
비어 있을 때만 싣는데, 내려놓고 나서 **먼저 만나는** 적치대에서 이미 차 버린다.
화면에는 「역이 넷이고 다 잡혔다」로 보이고, 값으로는 한쪽 종류가 영영 안 온다.
`usedLoads` 로 못 박고 인스펙터가 경고한다.

### 튜토리얼을 **글로** 읽었다

그전까지 확인한 것은 「가리키는 칸이 그때 화면에 있는가」였다. 문장을 순서대로
읽으니 네 곳이 나왔다. 그중 둘이 같은 종류였다 —

- 「나눠 쓰기」는 걸음이 다 「해 보기」라 분모가 0 → **열자마자 「다 했습니다」**
- 「원가 보기」 1번이 자재비까지 시켜서 3번이 **손도 안 댔는데 체크**

**셀 것이 없는 것과 다 한 것은 다르다.** 고르는 화면은 이미 갈라 두었는데
갈래 안이 안 따라와 있었다.

### 반복 실행이 라인의 **절반만** 돌고 있었다

천장과 잰 값을 나란히 놓으려다 나왔다. 「여러 판」의 처리량이 **어떤 도면에서든
0** 이었는데, 화면은 「출하 경로를 놓아야 잡힙니다」라고 말했다. 도면 탓으로
읽히는 문구인데 실은 **돌리는 쪽이 옮기지를 않고 있었다** — `runOnce` 가
`runMachines` 하나만 불렀다. 설비는 만들고, 만든 것은 아무 데도 안 갔다.

같은 도면 10분: 붙이기 전 **0개**, 붙인 뒤 **189개** 출하.

> 지난 회차에 「0 ± 0 개/시」를 보고 **설명 문구를 붙였다.** 값이 이상하면
> 먼저 왜 그런지 끝까지 가 봐야 한다 — 말이 되는 설명은 버그 위에도 붙는다.

## 16회차 — 도구가 옮겨 보고 값을 잰다 (배치 탐색)

### 무엇을 줄이는가

**개당 거리 하나다.** 배치를 바꿔서 달라지는 것이 그것이기 때문이다 — 라인의
천장은 공정 시간과 벨트 속도가 정하지, 설비가 어디 앉아 있는지가 정하지 않는다.
그래서 「처리량을 올리는 배치를 찾아 줘」는 이 탐색이 답할 수 있는 질문이 아니다.
화면이 그 사실을 못 박아 말한다 — 안 적으면 「손봤는데 왜 처리량이 그대로냐」가 된다.

### 왜 맞바꾸기만 하나

빈 땅으로 흩어 놓는 탐색은 값은 좋아지는데 **사람이 못 쓰는 도면**을 낸다.
맞바꾸기는 「어느 자리에 무엇을 둘까」라는 실제 결정이고, 무엇보다
**말로 옮길 수 있다** — 「제작기 1 과 조립기 2 를 맞바꾸세요」는 그대로 실행할
수 있는 지시다. 「제작기를 (12.75, −4.5) 로」는 그렇지 않다.

### 함정 검사가 함정이 아니었다

개당 거리는 나르는 양이 0 이면 함께 0 이 된다 — **경로를 부수면 점수가 좋아진다.**
가드를 넣고 되돌리기 테스트를 했는데 **안 물었다.** 코드가 아니라 검사가 틀렸다.

경로가 통째로 죽는 경우는 저절로 걸러진다(못 도는 카트 → 라인 천장 0 → 못 잰다).
진짜 위험한 것은 **일부만 갉아먹는** 맞바꾸기였다 — 먼 역 하나가 빠지면 라인이
조금도 나아지지 않았는데 평균 거리가 뚝 떨어진다(117.9 → 83.8, 정직한 최선보다 좋다).

> **되돌리기 테스트가 안 물면 코드가 아니라 검사를 먼저 의심할 것.**
> 「통과했다」와 「지키고 있다」는 다른 말이다.

### 도면을 마음대로 안 바꾼다

찾은 것을 목록으로 내놓고 **적용은 사람이 누른다.** 자동으로 고쳐 놓으면
「내가 그린 것」이 아니게 되고, 그러면 값이 좋아져도 안 쓴다. 적용은 한 번의
`MOVE_MANY` 라 Ctrl+Z 한 번으로 통째로 돌아간다.

---

### 이어진 요청 — 통로 안에서 옮기기

맞바꾸기만으로는 자리가 부족한 도면에서 아무것도 못 한다. 빈 자리로 옮기는 수를
더하면서 **통로**를 먼저 정해야 했다 — 안 그러면 카트가 다니던 길 한복판에 설비를
세운다(실제로 통로를 안 보고 돌리면 셋이 올라앉았다).

그런데 **여유를 두면 안 된다.** 정차역은 경로가 설비 포트 1 m 안을 지나야 생기고
포트는 바운딩 박스 안쪽에 박혀 있어서, 멀쩡히 도는 도면도 경로가 풋프린트 바깥
0.2 m 를 지난다. 여유를 1 m 로 두면 **정상 배치가 전부 불법**이 된다.
지킬 것은 하나였다 — **길 위에 물건을 놓지 마라.**

그리고 **통로 검사가 또 저절로 통과했다.** 바로 앞에서 밟은 것과 같은 실수다 —
가드가 있으나 없으나 같은 도면으로는 가드를 검사할 수 없다. 길이 라인을 가로지르는
도면으로 바꾸니 물었다.

## 17회차 — 상용과 견주어 빠진 것부터 채운다

### 요청

1. 다른 스마트 팩토리들과 견주어 **추가할 기능을 리스트업**
2. 그 **추천 순서대로** 진행

리스트업한 10가지 중 1~4순위를 순서대로 했습니다 — 로트 전환 · 흔들림의 모양 ·
손잡이 돌리기 · 배치 공정. 1순위의 나머지 절반이던 품종 전환도 이었습니다.

### 「얹기 쉽다」고 한 추천이 **틀렸다**

1순위를 「셋업·품종 전환, 얹기 쉬움」이라고 적었는데, 손을 대 보니 이 도구는
**한 설비 = 한 레시피**였습니다. 바꿀 품종 자체가 없으니 품종 전환을 얹을 수가
없었습니다. 그래서 둘로 갈랐습니다.

| | 무엇 | 크기 |
|---|---|---|
| **로트 전환** | 「N개마다 T초 쉰다」 — 날 갈기·금형·청소 | 파일 3개 |
| **품종 전환** | `recipe` 하나를 `recipes` 여럿으로 | 파일 9개 |

값이 큰 절반을 먼저 냈습니다. 실제 공장의 셋업 손실은 「N개마다 T초」 한 줄로 꽤
정확히 근사되고, 그 자체로 **다품종 공장에서 진짜 병목인 경우가 흔합니다.**

> **이름을 값에 맞춰 붙였습니다.** 품종이 하나뿐인데 「품종 전환」이라 부르면
> 화면이 거짓말을 합니다. 그래서 처음엔 그 낱말을 검사로 막았고, 품종이 여럿이
> 된 뒤에는 **이름이 품종 수를 따라가는지** 를 보는 검사로 바꿨습니다.

### 흔들림에 **모양**이 있다 — 그리고 내가 쓴 설명이 틀렸다

시간 편차 ±30% 를 주면 그동안은 균등분포였습니다. 실제 공정은 그렇지 않아서
네 모양을 뒀습니다(균등 · 종 · 꼬리 · 뾰족). **평균은 넷 다 1** 로 맞췄습니다 —
모양을 바꿨을 뿐인데 천장이 움직이면 견줄 수가 없습니다.

문서에 「꼬리 없는 분포로 돌리면 버퍼를 작게 잡는다」고 적었는데, 재 보니
**반대**였습니다.

    같은 ±30% 에서 앞 설비가 막힌 시간 · 최대 배수
    균등 79초 (1.50) · 종 58초 (2.03) · 꼬리 55초 (2.68) · 뾰족 45초 (1.50)

균등분포는 **최대 배수가 가장 작은데 막힌 시간이 가장 깁니다.** 큰 값이 드물게
오는 게 아니라 **자주** 오기 때문입니다. 짐작으로 쓴 문장을 지우고 잰 표를 넣었고,
검사가 이 표를 붙들게 했습니다.

### 손잡이를 도구가 대신 돌린다 — **두 번 거짓말한 판정**

「카트를 몇 대 두면 되나」를 사람이 손으로 돌려 보고 있었습니다. 손잡이 하나를
골라 값을 훑고 **꺾이는 자리**를 찾아 주게 했습니다(`core/sweep.js`).

판정이 두 번 틀렸습니다.

1. **못 보고 넘겼다** — 적치대 691개/시 → 821개/시 를 「평평하다」고 했습니다.
   판마다 흔들림이 커서 Welch 로는 안 걸렸습니다. 같은 씨앗으로 짝지어 견주는
   **대응표본**으로 바꾸니 잡혔습니다.
2. **없는 차이를 봤다** — 이번엔 0.4% 차이에 「트럭을 두 대 더 사라」고 했습니다.
   통계적으로 유의하다고 **살 만한 것은 아닙니다.** 「의미 있는 차이」의 문턱을
   따로 뒀습니다(`SWEEP_TIE = 2%`).

> 있는 차이를 못 보는 것도, 없는 차이를 보는 것도 둘 다 **안 하느니만 못합니다.**

### 품종 전환 — 종류가 **끝까지** 따라가야 한다

일의 대부분이 여기였습니다. 예전엔 벨트 한 줄에 한 종류만 흘러서 **줄에 이름표
하나**면 됐습니다. 같은 벨트에 두 품종이 앞뒤로 실리는 순간 그게 무너집니다 —
실린 시각과 닿는 시각이 달라 **벨트가 길수록 엉뚱한 종류로** 쌓입니다.

그리고 품종이 바뀌면 앞머리에 옛 종류가 몇 개 남는데, 「덩어리는 꽉 차야 실린다」로
두면 그 자투리가 영영 안 빠져 **20개씩 만드는 설비가 18개에서 멈췄습니다.**
규칙 한 줄로 풀었습니다 — **뒤에 다른 종류가 서 있으면 그 줄은 더 안 자란다.**

### 이 기능의 값은 **계산과 실측이 만나는 것**

2초짜리 설비가 두 품종을 번갈아 만들면 제작품 1은 「2초에 하나」가 아닙니다.
천장을 안 나누면 두 배로 부풀고, 돌려 본 값이 절반으로 나옵니다 — 그러면 사람은
**시뮬이 틀렸다고 여깁니다.**

                          천장(계산)   실제(300초)
    품종 1 · 전환 없음      1800 개/시   1692 개/시
    품종 1 · 20개/30초      1029 개/시    972 개/시
    품종 2 · 20개/30초       514 개/시    468 개/시

셋 다 천장의 91~94% 이고, 그 차이는 벨트를 채우는 시간입니다 — **세 경우에
고릅니다.** 고르지 않았다면 셈이 틀린 것입니다.

### 배치 공정 — 계산은 맞는데 **돌리면 천장의 5%**

「오븐은 20개를 한 판에 굽는다」를 넣었습니다. 개당 시간은 공정 ÷ 판 크기라
한 줄이면 끝나 보였는데, 실제로 돌려 보니 **천장의 5%** 밖에 안 나왔습니다.
두 군데가 판을 몰랐습니다.

| | 무엇이 틀렸나 | 어떻게 드러났나 |
|---|---|---|
| **벨트 간격** | 공정 시간에서 간격이 나오는데 그게 한 판에 드는 시간이라, 20개 판이면 간격이 20배 | 벨트가 텅 빈 채로 돌았습니다 |
| **출력 자리** | 한 판치만 두면 다 굽고도 앞판이 빠질 때까지 서 있음 | 60초 오븐이 **정확히 120초**에 한 판씩 |

둘 다 **계산으로는 안 보이고 돌려 봐야 보이는** 종류였습니다. 그래서 천장과
실측을 다섯 도면에서 나란히 놓는 검사를 넣었습니다 — 이 기능의 값 자체가
「계산과 실측이 만난다」이기 때문입니다.

    설비                  천장       정상상태
    한 개씩 · 12초        300 개/시  298 개/시
    한 판 10개 · 120초    300 개/시  300 개/시
    한 판 20개 · 240초    300 개/시  280 개/시

**재는 창을 잘못 잡아 세 번 헤맸습니다.** 적치대가 200개에서 차서 오래 돌리면
라인이 통째로 서고, 그러면 어느 도면이든 같은 값이 나옵니다. 「비율이 다
똑같다」가 보이면 재는 쪽을 먼저 의심해야 했습니다.

### 재작업 — 붙이려다 **손대기 전 버그 둘**이 드러났습니다

「불량을 버리는 대신 다시 만든다」를 넣었습니다. 붙일 자리를 찾다 보니, 불량을
거르는 코드가 **벨트가 종점에 닿을 때** 있었습니다. 두 가지가 틀려 있었습니다.

| | 무엇이 틀렸나 |
|---|---|
| **카트 라인** | 거르는 자리가 벨트에만 있어서, **카트로 나르는 설비는 불량이 아예 안 나왔습니다** — 불량률을 올려도 값이 안 변합니다 |
| **화면** | 설비 한 대의 「· 양품률」 옆에 붙은 불량 개수가 **라인 전체 합**이었습니다 — 옆 설비의 불량을 이 설비가 뒤집어쓴 것처럼 보입니다 |

둘 다 재작업과는 상관없이 원래 있던 버그입니다. 새 기능을 붙일 자리를 찾는 일이
**있던 것을 다시 읽게 만들어서** 드러났습니다.

### 천장이 불량을 몰랐습니다

「천장 600 · 실제 544」. 이 도구가 계속 고쳐 온 갈림인데 불량에서는 남아 있었습니다.

    버릴 때        공정 ÷ (1 − 불량률)
    다시 만들 때   (공정 + 불량률 × 재작업) ÷ (1 − 불량률²)

재작업품도 같은 불량률을 한 번 더 지나므로 끝내 버리는 것은 **제곱**입니다.
「고치면 무조건 살아난다」로 두면 불량률을 아무리 올려도 양품률이 100% 가 되어
화면이 거짓말을 합니다.

**재작업 30초짜리는 천장이 396으로 내려앉습니다** — 같은 설비인데 능력이 3분의
2입니다. 재작업이 쌀 때는 버리는 것보다 낫고, 비싸지면 버리는 쪽이 낫습니다.
그 갈림이 돌리기 전에 나오는 것이 이 기능의 쓸모입니다.

### 검사가 **무작위로** 깨졌습니다

끝에서 끝까지 재는 검사가 한 번 「천장의 106%」로 깨졌습니다. `runOnce` 에
`seed` 를 넘겼는데 그건 읽는 값이 아니어서(`d.rand ?? Math.random`) 그냥
`Math.random` 으로 떨어지고 있었습니다. 불량은 동전 던지기라 판마다 다릅니다.

흔들리는 검사는 없는 것만 못합니다 — 깨지면 코드를 의심하는 대신 다시 돌리게
되니까요. 난수를 직접 먹이고 세 번 연달아 돌려 확인했습니다.

### 되돌려도 안 물리면 — 이번엔 **코드가 문제**였습니다

새 검사는 소스를 일부러 되돌려 무는지 확인합니다. 열한 가지 중 셋이 안 물렸는데,
그중 하나는 **검사가 아니라 코드**였습니다. 「기다림 한도가 0이면 있는 만큼
굽는다」는 줄을 지워도 다 통과했는데, 바로 아래 줄이 `기다린 시간 >= 한도` 라
한도가 0이면 늘 참이었습니다 — **애초에 아무 일도 안 하는 줄**이었습니다.

지금까지 다섯 번은 검사 탓이었는데 이번은 아니었습니다. 되돌려도 안 물리면
**검사를 고치기 전에 그 줄이 하는 일이 있는지 먼저 봐야 합니다.**

### 화면이 없으면 기능이 **안 닿는다**

`recipes` 를 적는 곳은 인스펙터 「만드는 것」 칸 하나뿐입니다. 바탕이 다 돌아도
여기가 없으면 쓸 수가 없습니다. 칩 한 줄로 두고 **한 번에 한 품종만** 보여 줍니다 —
재료·버퍼 자리·부족분이 다 품종마다 달라서 한 판에 펼치면 어느 줄이 어디 것인지
못 읽습니다.

## 18회차 — 남은 다섯을 한 번에

### 요청

> 검사 라우팅 · 디스패칭 규칙 · 달력/계획정지 · 컨베이어 병합분기 · 실적 보정
> 까지 전부다 이어서 작업 진행해줘

순서는 **의존이 정했습니다.** 갈래가 있어야 검사 라우팅이 되고, 손잡이 돌리기가
있어야 실적 보정이 됩니다.

### 새 표를 만들지 않는 것이 이번의 주제였습니다

다섯 중 셋은 **이미 있는 것에 한 칸을 더해서** 끝났습니다.

| | 새로 만들 뻔한 것 | 실제로 한 것 |
|---|---|---|
| **달력** | 요일·주차 달력 | 교대표 줄에 「쉼」 한 칸 |
| **검사 라우팅** | 검사대 · 불량 벨트 · 되돌림 경로 | 「불량품」 종류 하나 |
| **실적 보정** | 맞추기 엔진 | 손잡이 돌리기 표를 다르게 읽기 |

달력을 따로 만들었다면 교대표와 두 벌이 되어 반드시 어긋납니다. 검사대·불량
벨트·되돌림 경로를 따로 만들었다면 셋이 각자 규칙을 갖게 됩니다. **불량이 하나의
종류가 되는 순간** 갈래도, 재작업 스테이션도, 폐기장도 이미 있는 것들이 다 합니다.

### 멈추는 자리는 한 곳이어야 합니다

주말에는 설비도 벨트도 카트도 서야 합니다. 움직이는 것이 전부 `simStep` 에서
시간을 받아 가므로 **거기서 0을 주면 한 번에** 섭니다. 소비자마다 「쉬는 중인가」를
따로 물으면 반드시 하나를 빠뜨립니다 — 벨트만 주말에 도는 그림이 나옵니다.

다만 **달력은 쉬는 동안에도 흘러야** 합니다. 시계까지 멈추면 주말에 들어간 순간
영영 못 깹니다.

### 「첫 레시피만 본다」가 두 번 더 나왔습니다

품종 전환 때 고쳤던 것과 같은 종류의 버그가, 갈래를 붙이자 두 군데서 또 나왔습니다.

- 갈래 목록이 레시피 산출물만 봐서 **불량품 벨트가 조용히 무시**됐습니다
- 정지 판정이 벨트 종점을 「첫 레시피 산출물」로 봐서, 불량품만 싣는 벨트를
  「제작품 1 자리가 찼나」로 판정했습니다 — **400초에 5개**, 라인이 통째로 안 돌았습니다

기능을 하나 넓히면 **「하나뿐이라고 가정한 자리」가 전부 드러납니다.** 그게 이
프로젝트에서 새 기능을 붙일 때마다 반복된 일입니다.

### 손대기 전 버그가 또 나왔습니다

`resetRun` 이 출하·도착 **누계를 안 지우고** 있었습니다. 지표가 기준점을 따로 잡아
둬서 탈이 없었는데, 오더 진척을 누계로 세는 순간 **두 번째 판부터 오더가 이미 다 찬
것으로** 보입니다 — 디스패칭이 아무 일도 안 하게 됩니다.

새 기능을 붙일 자리를 찾는 일이 **있던 것을 다시 읽게 만들어서** 드러났습니다.
17회차의 카트 불량 버그와 같은 경로입니다.

### 커밋 안 한 수정을 또 날렸습니다

되돌리기 테스트 뒤 `git checkout` 으로 되살릴 때 커밋 안 한 수정이 같이 날아갑니다.
이번 세션에서만 두 번째, 전체로는 세 번째입니다. **되돌리기 전에 반드시 커밋** —
이제 그 순서를 지킵니다.

## 19회차 — 예열 자동 판정 · 민감도

### 요청

> 워밍업 민감도 순으로 작업해줘

### 앞 회차가 이 회차를 만들었습니다

「데울 시간」은 처음부터 **10초 고정**이었습니다. 한 개씩 6초에 만드는 라인에서는
그럭저럭 맞는 값이었는데, 18회차까지 오는 동안 **240초에 한 판을 굽는 오븐**과
**품종 순환**과 **재작업**이 생겼습니다. 그 라인에서 11초에 나온 값을 「측정 끝」
이라고 내놓으면 도구가 사람을 속이는 것입니다.

    「한 판 20개 · 240초」 라인
    t=  11초    0 개/시   ← 옛 동작은 여기서 답했습니다
    t= 300초   36 개/시
    t=1800초  252 개/시

**기능을 늘리면 예전에 맞던 상수가 틀린 값이 됩니다.** 이 프로젝트에서 되풀이된
일이고(첫 레시피만 보던 자리들, 카트가 불량을 안 걸르던 자리), 이번에는 그게
「상수 하나」의 모습으로 나왔습니다.

### 재서 판정하지 않았습니다

값이 평평해지는 것을 보고 판정하는 방법이 교과서에 있습니다(Welch·MSER). 안
썼습니다 — 셋이 걸립니다.

| | 무엇이 걸리나 |
|---|---|
| **표본** | 모자라면 아직 오르는 중인 곡선을 평평하다고 봅니다 |
| **되풀이** | 같은 도면이 판마다 다른 시점에 끝납니다 |
| **설명** | **왜 그만큼 기다리는지를 화면이 못 말합니다** |

도면에서 세면 셋이 다 풀리고, 그 셈이 그대로 화면 문장이 됩니다 — 「벨트 채우기
33초 + 가장 느린 설비가 한 판 내기 480초」.

### 민감도는 「값을 훑기 전의 물음」입니다

16회차에 만든 손잡이 돌리기는 **한 손잡이**를 골라 값을 훑습니다. 그 앞의 물음 —
애초에 어느 손잡이를 잡을까 — 은 여전히 사람 몫이었습니다. 손잡이가 여섯이면
여섯 번 훑고 표 여섯 개를 눈으로 견줘야 했습니다.

**「±20%」로 흔들 수가 없었습니다.** 손잡이 값이 대개 대수·개수라 2.4대 같은 것이
없습니다. 이웃 값으로 한 칸씩 흔드는 쪽이 더 정직하기도 합니다 — 현장에서 할 수
있는 변경은 「한 대 더」이지 「20% 늘리기」가 아닙니다.

### 조사 하나가 도구를 덜 미덥게 만듭니다

손잡이 이름이 도면에서 오므로 조사를 박아 둘 수가 없어서 「적치대 수용량**가**
가장 크게 흔듭니다」로 적히고 있었습니다. 받침을 보고 고르게 고쳤습니다.
사소해 보이지만 읽는 사람이 문장을 두 번 읽게 되고, 그만큼 덜 믿게 됩니다.

### 씬이 안 도는 판에서도 화면은 볼 수 있습니다

이번 판에서는 shim 을 넣어도 r3f 루프가 안 살아나 시계가 0에 멎었습니다. 그럴
때는 `metrics` 를 브라우저에서 직접 밀어 넣으면 **진짜 컴포넌트가 진짜 값으로**
그려집니다 — 씬만 못 보고 나머지는 다 봅니다. 그렇게 「예열 8분 00초 · 7분 30초
남음」과 HUD 의 「측정 중… 4분 09초 남음」을 확인했습니다.

## 20회차 — 축적형 컨베이어 · 품종별 불량

### 요청

> 축적형 컨베이어랑 품종별 불량 이어서 진행해줘

둘 다 **만들면서 드러난 한계**입니다. 처음 상용 비교 목록에는 없었고, 갈래와 검사
라우팅을 만들다가 「이건 안 되네」로 나온 것들입니다.

### 새 기능이 낡은 버그를 판다 — 이번이 가장 컸습니다

축적형 벨트는 「못 내린 것」을 세야 합니다. 그걸 세기 시작하니 **손대기 전부터
있던 누수**가 드러났습니다.

    900초에 제작기가 343개를 만들었는데 찾을 수 있는 것은 131개
    → 212개가 어디에도 없이 사라지고 있었습니다

「종점이 막히면 벨트가 서니 넘칠 일이 없다」고 여겼는데 틀렸습니다. **자리가 한
칸 남았는데 세 개짜리 덩어리가 닿으면** 하나만 들어가고 둘이 없어집니다. 벨트가
서는 것은 자리가 **하나도** 없을 때뿐이라, 그 사이가 늘 새고 있었습니다.

**어느 지표에도 안 나타납니다.** 처리량은 종점 기준이라 그대로고, 만든 개수만
늘어납니다. 그래서 여태 아무도 못 봤습니다.

이번 세션에서 같은 모양의 일이 네 번 있었습니다 — 카트가 불량을 안 걸르던 것,
`resetRun` 이 누계를 안 지우던 것, 예열 10초, 그리고 이것. **새 기능을 붙일 자리를
찾는 일이 있던 것을 다시 읽게 만들어서** 나옵니다.

### 좋아 보이는 결과가 나오면 그것부터 의심합니다

축적형을 처음 쟀을 때 「앞 설비 막힘 1016초 → **0초**」가 나왔습니다. 너무 좋아서
들여다보니, 위의 누수 때문이었습니다 — 앞 설비가 **허공에 만들고 있었으니** 막힐
일이 없었던 것입니다. 고치고 나니 11% 로 내려앉았습니다.

    비축적 200개 · 막힘 1016초    축적형 200개 · 막힘 901초 · 재공 두 배

그리고 **처리량은 같습니다.** 버퍼는 상류를 안 세울 뿐 하류의 능력을 못 올립니다.
늘어난 것처럼 적으면 사람이 벨트만 바꿔 놓고 처리량이 늘기를 기다립니다.

### 「안 하겠다」고 적어 둔 것을 하게 되면

품종별 불량은 19회차에 **안 한 이유까지 적어 뒀던** 것입니다 — 「종류가 갑절이
되어 모든 고르개가 두 배로 길어진다」.

요청이 오니 그 이유를 **다른 방법으로 없애야** 했습니다. 재료 고르개가 **이 도면이
실제로 내보내는 불량품만** 보태게 했습니다 — 불량을 안 내보내는 도면에는 한 줄도
안 늡니다. 반대하던 근거가 사라지니 하는 것이 맞았습니다.

### 되돌리기 테스트가 색을 잡았습니다

불량품 여섯의 색을 죽이는 자리에서 되돌리기가 **터졌습니다**. 들여다보니 두 개가
겹쳐 있었습니다 — `payload` 는 `rgb` 를 안 남기고(`color` 로 바꿔 넣습니다),
`shade` 는 0/1 깃발을 받습니다. 결과는 여섯이 전부 `#d1d1d1` 하나로 뭉개진 것.

색은 화면에서만 보이는 값이라 검사가 없으면 다음에 또 뭉개집니다. 「여섯이 서로
다른 색이다」를 넣었습니다.

## 검증에 대한 참고

이 프로젝트는 **브라우저 패널이 표시되지 않는 환경**에서 만들어졌습니다.
3D 화면을 눈으로 본 적이 거의 없고(사용자가 몇 번 확인해 주었습니다), 대신
**값으로** 검증했습니다. `npm test` 로 묶여 있어 언제든 다시 돌릴 수 있습니다.

- **순수 모듈** — `core/*.js` 를 그대로 불러 값으로
- **JSX 안의 계산** — 소스에서 **떼어 내** 실행합니다(`cut` + `new Function`).
  손으로 옮겨 적으면 **옮겨 적은 것을 검증**하게 됩니다
- **배선을 글자로** — 「이 함수를 저 자리에서 부르는가」를 소스에서 확인합니다.
  값만 보면 멀쩡한데 화면이 그 값을 안 보는 경우가 실제로 여러 번 있었습니다
- **라인 통짜** — 도면 한 벌을 세워 제작기 → 벨트 → 적치대 → 트럭 → 개구부까지
  **끝에서 끝까지** 돌립니다

### 실제 GLB 를 Node 에서 읽는다 (15회차)

설비 포트는 GLB 안의 노드 이름에서 나오므로, 모델이 없으면 설비가 얽힌 검사를
아예 못 했습니다. 막고 있던 것은 한 줄이었습니다.

```js
globalThis.self = globalThis;      // three 의 워커 감지가 self 를 읽는다
```

텍스처만 못 읽고(경고 한 줄) 노드 이름·좌표·바운딩 박스는 전부 나옵니다.
이제 **실제 모델 치수로** 도면을 세워 돌립니다(`tools/check/_models.mjs`).

### `vite build` 는 검증이 아니다

**문법만** 봅니다. 정의되지 않은 식별자, 빠뜨린 import, TDZ 를 전부 통과시킵니다 —
실제로 그렇게 화면이 통째로 멈춘 적이 두 번 있습니다(위 표 14번).

### 검사를 새로 쓰면 **일부러 깨뜨려 본다**

늘 통과하는 검사는 없는 것만 못합니다 — 「통과했다」는 말로 안심시키기 때문입니다.
위 표 18번이 그랬고, 그 뒤로는 새 검사마다 소스를 되돌려 무는 것을 확인합니다.
**그리고 그 파괴 테스트는 커밋한 뒤에 합니다** — 새 파일은 untracked 라
`git checkout` 으로 복구가 안 됩니다(14회차에 두 번 잃었습니다).
